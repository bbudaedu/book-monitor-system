# Context7 Integration Rules

## 強制使用 Context7 的情況

在進行任何程式碼實作時，**必須**先使用 Context7 查詢相關技術文件：

### 1. 開始新任務前
- 查詢任務中涉及的所有技術棧的最新文件
- 確認 API 使用方式和最佳實踐
- 檢查是否有新的功能或重大變更

### 2. 實作特定技術時
- **Neon PostgreSQL**: 查詢 `/neondatabase/serverless` 獲取連接和查詢最佳實踐
- **Electron**: 查詢 `/electron/electron` 獲取主程序和渲染程序通訊方式
- **Puppeteer**: 查詢 `/puppeteer/puppeteer` 獲取網頁爬蟲和 SPA 處理方法
- **Winston**: 查詢 `/winstonjs/winston` 獲取日誌配置和格式化選項
- **Jest**: 查詢 `/jestjs/jest` 獲取測試撰寫和模擬物件使用方式
- **Node.js**: 查詢 `/nodejs/node` 獲取內建模組和 API 使用方式

### 3. 遇到錯誤或問題時
- 立即使用 Context7 查詢相關錯誤解決方案
- 查詢最新的故障排除指南
- 確認是否有已知問題和解決方法

## 實作流程

每個任務的標準流程：

1. **Context7 查詢階段**
   ```
   使用 Context7 查詢: [技術名稱]
   主題: [具體功能或問題]
   ```

2. **文件審查階段**
   - 閱讀最新 API 文件
   - 確認範例程式碼
   - 檢查最佳實踐建議

3. **實作階段**
   - 根據 Context7 提供的資訊進行實作
   - 遵循文件中的建議模式
   - 使用推薦的錯誤處理方式

4. **驗證階段**
   - 對照 Context7 文件驗證實作正確性
   - 確保符合最新標準

## 專案特定技術棧

### 資料庫層 (Neon PostgreSQL)
- 連接池管理
- 事務處理
- 錯誤處理和重試機制
- 遷移腳本

### 前端層 (Electron)
- 主程序和渲染程序架構
- IPC 通訊
- 安全性設定
- 打包和分發

### 爬蟲層 (Puppeteer)
- 無頭瀏覽器管理
- SPA 內容等待
- 錯誤處理和重試
- 效能優化

### 通知層 (LINE API)
- 訊息格式和限制
- 錯誤碼處理
- 速率限制
- Webhook 設定

### 測試層 (Jest)
- 單元測試結構
- 模擬物件建立
- 異步測試處理
- 覆蓋率設定

## 強制檢查清單

在提交任何程式碼前，確認：

- [ ] 已使用 Context7 查詢相關技術文件
- [ ] 實作遵循最新的最佳實踐
- [ ] 錯誤處理符合官方建議
- [ ] 測試覆蓋核心功能
- [ ] 程式碼註解引用相關文件連結

## 範例使用

```markdown
任務: 實作 Neon 資料庫連接

1. Context7 查詢:
   - 查詢 `/neondatabase/serverless` 
   - 主題: "connection pooling and error handling"

2. 實作重點:
   - 使用官方推薦的連接池設定
   - 實作自動重連機制
   - 加入適當的錯誤處理

3. 測試驗證:
   - 測試連接失敗情況
   - 驗證連接池行為
   - 確認錯誤處理正確性
```

記住：**永遠不要假設你知道最新的 API 或最佳實踐，總是先查詢 Context7！**
